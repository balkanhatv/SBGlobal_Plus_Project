- Only edges listed here, plus a more-specific explicitly versioned domain policy referenced here, are allowed for the named major workflow. All other edges return `<MS>_STATE_INVALID`.

- Transition permission is `<namespace>.workflow.transition` unless the row names a stronger target permission.
- Direct state-column editing is prohibited.
- Cancellation/reversal/correction never deletes prior approved/financial/evidentiary history.
- Every successful edge writes the named state change, row-version increment, transition history, listed event and audit. **No implicit synchronous business side effect exists.** Additional domain mutation is allowed only when the owning MS section or DD-24 explicitly names it for that trigger; otherwise additional side effect = `NONE`. ## Deterministic side-effect / approval / notification resolution
For every transition row above the resolution algorithm is authoritative:
1. Apply exactly the row's state transition, increment `row_version`, append transition history, publish the row's named domain event, and write audit.
2. Look up the transition trigger in the owning MS canonical Business Rules and DD-24. If those documents explicitly name an additional synchronous mutation, approval authority or notification recipient, execute exactly that contract.
3. If no explicit rule exists, the value is **NONE**. There is no default inferred approval, mutation, email, push, document or financial effect.
4. Runtime configuration may select an already-declared recipient/channel/template/threshold only within DD-23/DD-24 policy bounds; it cannot create a new transition effect or weaken an approval/security floor.
5. A missing configured value for a mandatory declared effect returns `CONFIGURATION_INVALID` before the transition and produces zero business mutation/event.
