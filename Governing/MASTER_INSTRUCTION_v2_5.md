## 9A. Documentation Depth & Evidence Standard

A heading, a section title, a single summary sentence, a registry row, or a certification statement is never itself sufficient evidence that a required element (§9, §10) is complete. Each required element is satisfied only by content that could not have been produced without doing the underlying work:

- A **Business Rule / Validation / Policy** element is satisfied only by named, individually stated rules with their trigger condition and resulting action — not a bare mention that rules exist.
- A **Workflow / State** element is satisfied only by an enumerated state list, the transitions between them, and who or what triggers each transition — not a workflow name alone.
- An **Entity / Field / Relationship** element is phase-sensitive: Foundation must identify the business entity/concept, ownership, lifecycle and material relationships needed to establish WHAT/WHY/WHO; Architecture must establish ownership/boundaries, storage/data-flow responsibility and architectural relationships; **Detailed Design** owns exact field dictionaries, types, nullability, indexes, complete schemas and implementation contracts.
- A **Permission / RBAC / ABAC** element is phase-sensitive: Foundation must identify roles, permission intent and material contextual policies; Architecture must define the enforcement boundary/order and policy responsibilities; **Detailed Design** owns the exhaustive role-permission matrix and exact policy expressions.
- An **Architecture Decision** — including every ARCHITECTURAL-COMPLETION unit (§35) — is satisfied only when its authoritative decision record contains: Context, Decision, Alternatives / Options Considered, trade-off comparison (complexity, cost, scalability/maintainability, dependency impact), Consequences, and affected dependencies. A one-line note ("Decision: use X") is not sufficient evidence.
- An **API / Event / Integration** element is phase-sensitive: Foundation must define the required business interaction, actor/system purpose, authorization/ownership expectation and outcome; Architecture must define capability boundaries, interface responsibilities, event/API architectural contracts and system behavior; **Detailed Design** owns exact endpoint paths/methods, complete request/response schemas, exact payload structures, field-level contracts and implementation mechanics.
- A **Test / Acceptance** element is satisfied only by the actual test scenarios or acceptance conditions for the scope in question, per the applicable Engineering Standards test type (S2.3) — not a statement that testing occurred.

**NO CERTIFICATION WITHOUT EVIDENCE.** No status defined at §33A, and no certification defined anywhere in this document (Industry Specification Certification above, Production Readiness §27, Completion & Certification §33), may be granted on the strength of a label, a checklist checkbox, or a registry entry alone. The underlying evidence — satisfying the standard above — must exist and be traceable (§5) before the status or certification is recorded. This rule binds equally when a Foundation is rebuilt from zero: a prior or superseded Foundation's certifications are historical record only (§33A) and are never treated as evidence for a new build's status.

## 13. One Core Identity & Access System

**Login Entry Point ≠ Application Surface ≠ Identity System.** A separate login URL never means a separate authentication engine. All entry points (Platform, Tenant Management, Industry, Staff, Student, Customer, Patient, Mobile, Desktop) use the single Core Identity & Access system.

Centralized: Users, Credentials, Authentication, OTP, Passwordless, Magic Link, QR Login, Passkeys (FIDO2/WebAuthn), Authenticator/TOTP, Hardware Keys, Biometrics, MFA/Step-Up, SSO, OAuth 2.0, OIDC, SAML 2.0, LDAP/AD, API tokens & service accounts, Clerk-managed sessions/access tokens through the provider-isolated Core identity boundary, Device Identity & Registration, RBAC (Roles, Permissions, Groups), Authentication/Authorization/Security Policies, Risk-based adaptive authentication (trusted/unknown devices, impossible travel, geo-fencing/restriction, time restrictions, concurrent session control), Digital Identity & Signature providers (Aadhaar eSign, DigiLocker, DSC/PKI, eTokens), Identity & Authorization Audit. Machine API credentials and service accounts remain a separate governed credential path; they are never represented as human refresh sessions.

Never create separate authentication engines for Platform, Tenant, any Industry, Mobile, Desktop, or Management Systems. Policies remain configurable per Tenant, User, Group, Department, Organization, Device, Platform, Module, Location, and Subscription Plan.

**Server-Authoritative Architecture:** every business operation requires User Authentication · Tenant Validation · Subscription Validation · License Validation · Device Registration Validation · Role & Permission Validation · Clerk Session/Access-Token Validation for human sessions or separate Machine API Credential Validation for API clients/services · API Authorization — enforcing the entitlement chain (§21) at every step. Offline mode only for previously-authenticated, authorized users under configurable sync/security policy.

**Authorization Model — RBAC (Primary) + ABAC (Complementary):** RBAC (Roles, Permissions, Groups — above) is the PRIMARY authorization model. ABAC (Attribute-Based Access Control) is a COMPLEMENTARY contextual authorization/policy layer, used when an access decision needs contextual attributes such as Tenant, Industry Context, Department, Branch, Location, Device, Time, Subscription, License, Data Sensitivity, Risk Context, and other explicitly governed attributes. ABAC extends RBAC for fine-grained, context-aware authorization; **ABAC never replaces RBAC.** The ABAC layer stays inside this one Core Identity & Access system — never a separate authorization engine per Industry or Tenant — respects Tenant isolation (§20) and Industry Context (§7), remains compatible with the RBAC model above, stays server-authoritative (above) and auditable (Identity & Authorization Audit, above), and remains configurable/policy-driven where appropriate. Canonical authorization decision:

```
RBAC permissions
   + Applicable ABAC policies
   + Tenant/Industry Context (§7)
   + Security constraints (§20)
   + Subscription/License constraints (§21)
   → Final Authorization Decision
```

## 23. GitHub & Source Control Governance

## 26A. Phase Gate Model

Phase count remains dependency-driven (§26) — this section defines the gate every phase passes through, not a fixed phase list or an added phase count. Whatever phases dependency analysis yields, each is opened and closed only against this template:

- **Objective** — what the phase exists to accomplish, in one statement.
- **Scope** — exactly which Industries, Management Systems, Modules, or layers this phase covers, and which it explicitly excludes.
- **Mandatory deliverables** — the concrete artifacts the phase must produce.
- **Mandatory documentation** — which canonical documents/sections this phase's work must land in, satisfying §9A depth.
- **Required evidence** — the specific proof, per §9A, that the deliverables are real — not the deliverables' existence alone.
- **Required dependencies** — which prior phases, decisions, or external inputs this phase consumes, and their required status (§33A).
- **Required validation** — the checks (peer review, architecture review, security review) the deliverables pass before the phase can close.
- **Required tests/audits** — which of §5's traceability audits, §20's security/tenant-isolation tests, or Engineering Standards (S2.3) test types apply.
- **Required registers** — which of the §30 mandatory registers (D-INDEX, D-DECISIONS, D-CHANGELOG, Traceability Matrix, No-Loss Audit, REVIEW_REQUIRED) must be updated.
- **Required checkpoint artifacts** — the §24 checkpoint package contents specific to this phase.
- **Entry criteria** — the prior phase's exit status (§33A) and any Blocking Conditions (§32) that must be clear before this phase may begin.
- **Exit criteria** — the status (§33A) this phase's scope must reach, backed by the evidence above, before the phase is reported complete.
- **Explicit deferred items** — anything knowingly left for a later phase, logged by name in REVIEW_REQUIRED or D-DECISIONS rather than silently dropped.

A phase is never certified complete because a small number of summary files exist; it is certified complete when every applicable item above is satisfied for its declared scope.

## 26B. Detailed Design / Implementation Specification Gate

Between Architecture and Development (§26) sits a mandatory **Detailed Design / Implementation Specification** stage, recurring once per build-scope (§26). Architecture (Part II) establishes the high-level model — component boundaries, data flow, API contracts at the capability level, storage choices, and their recorded trade-offs (§9A) — it does not, by itself, define implementable detail. Development may not begin on a given scope until that scope's Detailed Design reaches DETAILED DESIGN COMPLETE (§33A), covering, where applicable to the scope:

Core Modules · Management Systems (§10) · Entities, Fields, Relationships · Business Rules · Validation · Workflows · States · Approvals · Permissions · RBAC · ABAC (§13) · APIs · Events · Integrations · UI/UX · Mobile · Desktop (§15, §19) · AI · RAG · Automation (§16) · Master Data · Seed Data · Demo Data (§18) · Testing · Security (§20) · Migration · Rollback · Dependencies · Operations.

Each covered item is documented to the §9A depth standard — concrete enough that Development could proceed without re-deriving the design. ARCHITECTURE CERTIFIED and DETAILED DESIGN COMPLETE are distinct, sequential statuses (§33A); neither may be inferred from the other, and a scope may be Architecture Certified while its Detailed Design remains in progress — but Development on that scope may not start until Detailed Design Complete is reached for it.

## 33A. Status & Certification Lifecycle

Every scope — a Knowledge Unit, a Management System, an Industry Suite, a Core Platform capability, or the project as a whole — progresses through the following statuses. A status is granted only per §9A (no certification without evidence); no earlier status is ever treated as proof of a later one, and a status may not be skipped:

**DISCOVERED → SPECIFIED → FOUNDATION CERTIFIED → ARCHITECTURE CERTIFIED → DETAILED DESIGN COMPLETE → IMPLEMENTED → TESTED → SECURITY VALIDATED → PRODUCTION READY → DEPLOYED → OPERATIONAL**

- **DISCOVERED** — the scope is identified (in the corpus, §3–§4, or by user instruction, §2) but not yet classified or written up.
- **SPECIFIED** — the scope is classified (§6, §35) and documented to §9A depth; for a Current Supported Industry, this is the level Industry Specification Certification (§9) validates.
- **FOUNDATION CERTIFIED** — the scope's canonical documentation is complete, traceable (§5), and free of unresolved REVIEW_REQUIRED items material to it.
- **ARCHITECTURE CERTIFIED** — the scope's high-level design (component boundaries, data flow, API contracts, storage choices) is recorded with trade-offs in D-DECISIONS (§9A's evidence requirement) and conforms to the Canonical Architecture Model (Part II).
- **DETAILED DESIGN COMPLETE** — the scope satisfies §26B in full.
- **IMPLEMENTED** — the scope's code/configuration exists and matches its Detailed Design.
- **TESTED** — the scope passes the applicable Engineering Standards test types (S2.3) and, where relevant, Tenant Isolation testing (§20).
- **SECURITY VALIDATED** — the scope passes the security posture defined in §20.
- **PRODUCTION READY** — the scope passes every §27 acceptance gate.
- **DEPLOYED** — the scope is live per §27's deployment definitions.
- **OPERATIONAL** — the scope is in ongoing service: monitored, backed up (§24), and covered by a support/incident process. This is the evidence required wherever this document or MASTER_PROMPT.md refers to a scope's "Operations" stage (§26).

Industry Specification Certification (§9) and Production Readiness (§27) remain the named gates they always were — this ladder makes explicit which single status each corresponds to, and adds the intermediate statuses the corpus and prior editions left implicit. Completion & Certification (§33) requires every in-scope item to have reached the terminal status its nature requires: OPERATIONAL for live scopes, PRODUCTION READY at minimum for a completed but not-yet-deployed build.

**Zero-Start Foundation Rule.** When a Foundation is rebuilt from zero, a prior or superseded Foundation's statuses are historical record only (§34) — they are never carried forward as evidence for the new build. The new build earns every status in this ladder on its own evidence, produced fresh at the appropriate depth (§9A); a previous build having reached a given status is not itself proof that the new one has.
